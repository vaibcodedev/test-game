# Библиотеки для «Пепельного Предела»: что взять, что оставить своим

Исследование от 28.10.2026. Код не менялся, пакеты не ставились. Версии и даты релизов сверены с реестром npm (`npm view`) и официальной документацией в тот же день.

**Коротко для владельца.** Большая часть нашего «самописного» кода уже хорошая и заточена под игру: поиск пути, ИИ мобов, звук, тени, сглаживание движения, защита от флуда, переподключение. Менять их на библиотеки — потратить время и получить хуже. Реальную пользу дадут **несколько точечных** вещей:

1. **ускорить загрузку и отрисовку на слабом ПК:** собрать ~730 картинок объектов в атлас;
2. **закрыть дыры в проверке сообщений от игроков:** схемы zod;
3. **автообновление ПК-клиента:** electron-updater, он уже почти стоит в проекте;
4. **инструменты разработчика, которые не попадают в игру:** поиск мёртвого кода, линтер, нагрузочный тест сервера.

Из четырёх идей владельца пригодится одна: **@colyseus/loadtest** (строго версии 0.16.2). Rex UI, EasyStar.js и Howler.js нам не нужны, почему — в разделе 5.

Есть два крупных решения, которые не стоит принимать сейчас:
- **Phaser 3.90 → Phaser 4.** Phaser 3.90 — последняя версия третьей ветки, Phaser 4 вышел в апреле 2026.
- **Colyseus 0.16 → 0.18.** В 0.18 есть встроенное предсказание движения, проверка сообщений и лимит сообщений.

Оба перехода — отдельные большие этапы. Сначала вывести игру к релизу, потом переезжать (раздел 6).

## 3. Подробно по каждой рекомендованной библиотеке

### 3.1. Атлас текстур: `maxrects-packer` (+ уже стоящий `pngjs`)

- Ссылки: https://github.com/soimy/maxrects-packer, https://www.npmjs.com/package/maxrects-packer, загрузчик атласа Phaser: https://docs.phaser.io/api-documentation/class/loader-loaderplugin#atlas
- Версия: рекомендую `2.7.4` (вышла 28.08.2025, проверенная). Ветке `3.0.0` всего две недели (15.10.2026, ESM + CJS). Брать её только после проверки, что API размещения не поменялся.
- Лицензия MIT. В игру не попадает: работает только в `tools/`.

**Что даёт нам.**
- `BootScene.ts` в цикле грузит каждую картинку отдельно: `for (const id of Object.keys(m.objects)) this.load.image(\`o_${id}\`, …)`. Это **729 файлов** объектов, 5,3 МБ. Плюс 264 листа юнитов (34 МБ) и 177 листов VFX.
- Каждый отдельный файл — это HTTP-запрос и отдельная текстура в видеопамяти.
- WebGL-рендер Phaser 3 рисует пачкой, пока подряд идут спрайты из ограниченного числа текстур (обычно 8–16 слотов). Лес из десятка разных деревьев, домов и декора постоянно рвёт пачки, поэтому растёт число вызовов отрисовки. Это как раз то, что `tests/perf-run.ts` считает как «вызовы отрисовки GL».
- После атласа все объекты лежат в 2–4 больших текстурах, и на слабой встроенной видеокарте это заметно.
- Иконки (2234 файла) — это DOM `<img>`, браузер грузит их лениво, и переделывать их не нужно.

**Где подключить.**
- `tools/gen-assets.ts`: после того как объекты записаны в `client/public/assets/objects/*.png` (строки 52–53 и 126), запускается новый шаг `tools/gen/atlas.ts`.
- `client/public/assets/manifest.json`: новое поле `atlases: [{ key, png, json }]`.
- `client/src/game/BootScene.ts`: `this.load.atlas("objs0", "/assets/atlas/objs0.png", "/assets/atlas/objs0.json")`.
- Места с ключом `o_…`, 10 вызовов: `BootScene.ts`, `GameScene.ts`, `terrain.ts`, `siegeView.ts`, `towerArchers.ts`.

**План миграции.**
1. Написать `tools/gen/atlas.ts`.
   - Прочитать PNG объектов через `pngjs`.
   - Разложить их через `MaxRectsPacker(2048, 2048, 2, { smart: true, pot: false, allowRotation: false })`. Отступ 2 px и экструзия краёв на 1 px, иначе при дробном зуме появляются «швы» — особенно важно для пиксель-арта.
   - Склеить листы и записать JSON в формате Phaser «JSON Hash»: `frames[id] = { frame:{x,y,w,h}, sourceSize, spriteSourceSize }`.
   - Размер листа не больше 2048×2048: это безопасно для слабых и старых GPU.
2. Записать в `manifest.json` список атласов и карту `id → атлас`.
3. Сделать в клиенте единую функцию `objTex(id): [key, frame]` в новом `client/src/game/objTex.ts` и перевести на неё 10 мест с `o_${id}`. Тени (`shadows.ts`) берут кадр самого спрайта, поэтому заработают сами.
4. Оставить запасной путь: если атласа нет (старый `manifest`), грузить по одному. Так можно откатиться.
5. Проверить производительность. Следующим шагом так же упаковать мелкие листы юнитов (NPC, мобов): их кадры остаются кадрами внутри атласа, анимации Phaser создаются из `frames` атласа.

**Что удалить из своего кода.** Цикл `load.image` по объектам в `BootScene.ts`. Раздачу `client/public/assets/objects/` в `dist` можно убрать после проверки: исходники остаются в `tools/out`.

**Как проверить.**
- `tests/perf-run.ts --label=before` и `--label=after` (строго по одному запуску): сравнить число вызовов отрисовки и p95 времени кадра в лесу и в городе.
- `tests/screenshot.ts` и `tools/shadows-shots.ts`: картинка должна совпасть с прежней.
- `npm run typecheck`.

**Подводные камни.**
- Без экструзии краёв и отступа при зуме 2,25 появляются цветные полоски по краю спрайта.
- Не включать `allowRotation`: Phaser поддерживает повёрнутые кадры, но тени и `hoverGlow` считают размеры по `frame.width` и `frame.height`.
- Генератор запускается в `predev` и `build`: упаковка должна быть быстрой и не трогать неизменённые файлы. Можно кешировать по хешу списка.

- Ссылки: https://zod.dev, https://www.npmjs.com/package/zod. `validate()` в Colyseus 0.18 на zod: https://docs.colyseus.io/room
- Версия `4.6.7` (12.10.2026), MIT.
- Альтернатива — `valibot` 1.5.0 (https://valibot.dev): меньше по размеру, но размер бандла важен только клиенту, а схемы нужны на сервере. Выбираю zod, потому что именно его принимает встроенный `validate()` будущего Colyseus 0.18: схемы перенесутся без переписывания.

**Что даёт нам.**
- Сейчас ~80 обработчиков (`WorldRoom.ts` — 61, `common.ts` — 12, плюс `RaidRoom` и `DungeonRoom`). Каждый вручную проверяет `typeof m.id === "string"`, `num(...)`, `Object.hasOwn(...)`.
- Проверки хорошие, но легко забыть поле. Пример: в `WorldRoom.ts:729` `String(m.faction) as …` — значение приводится к типу без проверки по списку фракций (обработчик админский, но всё равно).
- Схема на каждое сообщение даёт:
  - гарантию, что лишние и неверные поля не проходят;
  - тип сообщения выводится из схемы (`z.infer`), поэтому не нужно писать `on<{ id: unknown }>` руками;
  - схемы можно положить в `shared/protocol.ts`, и клиент будет отправлять типизированные сообщения.

**Где подключить.**
- `server/src/rooms/common.ts`: новая перегрузка `on(type, schema, fn)` внутри `makeOn`. Порядок такой: `floodCheck`, потом `schema.safeParse(msg)`, при ошибке тихо отбросить (не отключать), потом `fn(p, parsed.data)`.
- Схемы: `shared/messages.ts` (новый) или `shared/protocol.ts`.
- Числовые пределы брать из `data/server.json` и `shared/constants.ts` (`CHAT_MAX_LEN`). Свою `cleanText` подключить через `.transform(cleanText)`.

**План миграции.**
1. Добавить `zod` в `dependencies` (сервер бандлится esbuild в `desktop/scripts/bundle.ts`, это проверить).
2. Сделать обёртку в `makeOn`, старая сигнатура без схемы продолжает работать.
3. Переводить по группам: движение и бой (`common.ts`), потом торговля (`server/src/trade/TradeManager.ts`), банк, сумки и предметы (`rooms/items.ts`), админ, остальное. Одна группа — одна мелкая задача.
4. Проверки «по смыслу» (хватает ли золота, рядом ли NPC) остаются в коде игры. Схема проверяет только **форму** сообщения.

**Что удалить.** Повторяющиеся `typeof … !== "string"` и `num(...)` внутри переведённых обработчиков. Сами `num` и `cleanText` оставить, они пригодятся в схемах.

**Как проверить.**
- `tests/server-safety.ts`: дописать мусорные сообщения (строка вместо объекта, `NaN`, `Infinity`, `__proto__`, длинные строки).
- `tests/trade.ts`, `tests/bank.ts`, `tests/combat.ts`, `tests/admin.ts`.

**Подводные камни.**
- Не отключать клиента при ошибке схемы. `validate()` в Colyseus 0.18 по умолчанию отключает с кодом 4002, а у нас сознательно выбрано «тихо отбросить» (см. комментарий про 4002 в `makeOn`). Обновлённый клиент со старым сервером не должен вылетать.
- `z.object` по умолчанию отбрасывает лишние ключи, это нам и нужно. `.strict()` не включать.
- Для горячего пути (`input` раз в кадр) схема должна быть простой: `z.object({ mx: z.number().min(-1).max(1), … })`. Zod 4 на таком быстр, но всё равно стоит замерить в `tests/bots.ts`.

### 3.3. Автообновление ПК-клиента: `electron-updater`

- Ссылки: https://www.electron.build/auto-update, таблица целей: https://www.electron.build/docs/targets/, безопасность обновлений: https://www.electron.build/docs/features/security/
- Версия `6.8.11` (20.10.2026), MIT, тот же проект, что и уже стоящий `electron-builder` 26.

**Что даёт нам.** Сейчас в `desktop/electron-builder.yml` стоит `publish: null`, обновления только ручные. С `electron-updater`:
- лаунчер при старте проверяет новую версию;
- качает только изменившиеся блоки (файл `.blockmap`), а это важно при 76 МБ ассетов;
- после закрытия игры ставит обновление.

**Где подключить.**
- `desktop/electron-builder.yml`: `publish: { provider: generic, url: https://<ваш-хостинг>/updates/ }` или `provider: github` (GitHub Releases, бесплатно).
- `desktop/src/main.ts`: `import { autoUpdater } from "electron-updater"`, проверка после `app.whenReady()`, вывод статуса в `desktop/launcher/launcher.ts`.
- `desktop/scripts/before-build.cjs` и `bundle.ts`: `electron-updater` должен попасть в `desktop/out/app` (у нас своя сборка `package.json` без `node_modules`, это проверить).

**План.**
1. Решить, где лежат файлы обновлений (GitHub Releases или любой статический хостинг).
2. Настроить `publish` и собрать две версии подряд (0.1.0 → 0.1.1), проверить обновление на чистой машине.
3. Подписи кода у нас нет, поэтому в `win` поставить `verifyUpdateCodeSignature: false`. Иначе обновление будет отклонено, а сборка упадёт на проверке издателя. Это осознанный компромисс; лучший вариант — купить сертификат и включить проверку обратно.
4. В лаунчере показать «Доступно обновление → Перезапустить».

**Что удалить.** Ничего, это новая возможность.

**Как проверить.** `npm run desktop:smoke`. Ручной сценарий: установить старую версию, выложить новую, запустить и убедиться, что обновилось, а база в `%APPDATA%\AshenReach` цела.

**Подводные камни.**
- **Portable-сборка автообновляться не умеет**: в таблице целей electron-builder у `portable` указано «Manual». Её оставить для ручного скачивания.
- Без подписи SmartScreen будет предупреждать при установке.
- Встроенный сервер и `dist` лежат в `extraResources`, они обновятся вместе с приложением. Миграции базы (раздел 3.5) должны уметь поднять старую базу.

### 3.5. Миграции БД: своё на `PRAGMA user_version`, библиотека не нужна

### 3.6. `knip` — поиск мёртвого кода

- Ссылки: https://knip.dev, https://www.npmjs.com/package/knip. Версия 6.43.0 (24.10.2026), ISC.
- **Что даёт.** В `tools/` и `tools/gen/` десятки разовых скриптов (`bf-gen`, `bf-gen2`, `*-shots`, `*-preview`), в `tests/` — скриптовые прогоны. Knip показывает неиспользуемые файлы, экспорты и зависимости. Меньше кода — меньше читают агенты, а значит, дешевле каждая задача.

- **Подводный камень.** Скрипты, которые запускают только руками (генераторы боссов), knip посчитает мёртвыми. Их нужно перечислить в `entry`.

### 3.7. `@biomejs/biome` — линтер

- Ссылки: https://biomejs.dev, https://www.npmjs.com/package/@biomejs/biome. Версия 2.6.3 (24.10.2026), MIT или Apache-2.0.
- Один нативный бинарник, без сотни плагинов ESLint, поэтому лёгкий для слабого ПК.

### 3.11. По желанию: `lit-html`, `ZzFX`, `@colyseus/monitor`, `node:test`

**lit-html 3.3.3** (BSD-3, https://lit.dev/docs/libraries/standalone-templates/)
- Шаблоны `` html`<div>${name}</div>` `` экранируют подстановки сами. Сейчас защита от XSS держится на том, что в каждом из 140 мест с `innerHTML` не забыли `esc()`: имена героев, чат, названия предметов.

- Все 140 мест разом не переписывать.

**ZzFX 1.4.0** (MIT, https://github.com/KilledByAPixel/ZzFX)
- Крошечный (~1 КБ) синтезатор с веб-редактором: звук задаётся строкой чисел, её удобно хранить в `data/sfx.json`.

- Наши громкость, mute и музыка остаются своими: ZzFX подключается к нашему `master` GainNode.
- Не обязательно.

**@colyseus/monitor 0.16.7** (MIT, https://docs.colyseus.io/tools/monitor)
- Веб-страница со списком комнат, игроков и состоянием, можно отключить клиента.
- Подключается в `server/src/index.ts` одной строкой `app.use("/colyseus", basicAuth(...), monitor())`.
- **Обязательно за паролем** и не в ПК-сборке.

**node:test** (встроен в Node, https://nodejs.org/api/test.html)
- Для новых чистых модульных тестов (формулы, схемы zod, склонения) вместо самописных `check()` и `assert()`: таймауты, понятный отчёт, `--test-only`.
- Существующие интеграционные тесты не трогать.
- Запуск с `--test-concurrency=1`, потому что сценарии с сервером идут строго по одному.

## 4. Что оставить своим и почему (сильные стороны проекта)

- **Поиск пути (`shared/path.ts`).**
  - A* по клеткам на двоичной куче, с общими буферами `Float64Array` (без мусора на каждый поиск), без срезания углов, со сглаживанием по прямой видимости `segmentWalkable` для круга радиуса r, с лимитом узлов `maxNodes`.
  - Он **общий для клиента и сервера** и знает наши интерьеры (`interiorGrid`).
  - Любая библиотека потребует переводить карту в её формат и потеряет учёт радиуса и интерьеров.
- **ИИ мобов.**
  - Простая машина состояний + поведения из `data/mobAI.json` (kite, heal, slam, throw). Это правильный уровень сложности и он уже управляется данными.
  - Боссы — сценарии по фазам; деревья поведения дали бы больше кода, а не меньше.
- **Звук (`sfx.ts`).**
  - Процедурный WebAudio без файлов: ноль загрузки и ноль мегабайт.
  - Громкости, mute, музыка зон и защита от слишком частого повтора (`lastPlay`) уже есть.
  - Если появятся настоящие файлы музыки (ogg), их проще всего декодировать тем же `AudioContext` (`decodeAudioData`) или загрузчиком Phaser `this.load.audio`. Отдельный Howler не нужен.
- **Сглаживание сетевого движения (`UnitView.ts`).** Подстройка под фактический интервал пакетов (`ivl`), постоянная скорость вместо экспоненты, телепорт при разрыве больше 160 px. Это продуманное и проверенное `perf-run` решение.
- **Защита от флуда (`floodCheck`).** Отдельные лимиты для движения и прочего, отключение после серии окон, тихий отброс неизвестных сообщений. Лучше, чем `maxMessagesPerSecond` в новых Colyseus: тот просто отключает.
- **Переподключение (`client/src/net.ts`, `allowReconnection`).** Работает и покрыто `tests/reconnect.ts`.
- **Ошибки клиента.** `crash()` / `reportError()` с фильтром безвредных ошибок и лимитом, окно «Что-то пошло не так». Внешний Sentry для одной игры с одним владельцем избыточен и отправляет данные третьей стороне.
- **Генерация карты (`shared/map.ts`).**
  - Детерминированный шум одинаков на клиенте и сервере.
  - Замена на `simplex-noise` поменяет **весь мир**: придётся поднимать `MAP_VERSION`, все сохранённые позиции сбросятся, а `tests/map-layout.ts` придётся перенастраивать.
  - Никакой выгоды это не даёт.
- **Тени и ночь (`shadows.ts`).** Дешёвые тени из кадров с режимами Выкл / Простые / Динамические — как раз для слабого ПК. Light2D в Phaser 3 требует карты нормалей и дороже по GPU.
- **Окна, перетаскивание, подсказки, вкладки (`kit.ts`, `drag.ts`, `hud.ts`).** Малый объём, учитывают наш CSS zoom и масштаб интерфейса. Библиотеки ничего не добавят.
- **Тексты `T()`.** 10 строк, нужен только разбор склонений (3.4).
- **База на `node:sqlite`.** Встроенная, без нативной сборки под Electron, с бэкапами и транзакциями переноса предметов.

| **Howler.js** (2.2.4, последний релиз **сентябрь 2023**, https://github.com/goldfire/howler.js) | **Не брать** | Howler нужен для воспроизведения **файлов**, а у нас звук синтезируется кодом. Он дублирует `AudioContext` и наш микшер, а развитие фактически остановилось. Если появятся файлы музыки — встроенный `decodeAudioData` или загрузчик звука Phaser. |
| **@colyseus/loadtest** | **Брать, версия 0.16.2** | См. 3.8. Последнюю 0.18.x не ставить. |

### Другие популярные, но ненужные нам

- **GSAP.** У Phaser свои твины с теми же easing. Лицензия GSAP — собственная бесплатная, но не открытая (https://gsap.com/standard-license).
- **bitECS / любой ECS** (0.4.0, лицензия MPL-2.0). Переписывание всей модели `Player`, `Mob`, Schema ради скорости, которой и так хватает. Узкое место у нас в отрисовке, а не в логике.
- **mistreevous** (деревья поведения). Вернуться, только если ИИ боссов станет неуправляемым.
- **simplex-noise.** Меняет мир (раздел 4), последний релиз 2024 года.
- **better-sqlite3.** Нативный модуль: под каждую версию Electron нужна пересборка (`electron-rebuild`), это ломает простую сборку `desktop:build`. `node:sqlite` уже работает.
- **ORM** (Prisma, Drizzle, Kysely). Пять таблиц, сохранения в JSON-колонках. ORM добавит слой и миграции чужого формата.
- **i18next.** Пока игра только на русском, `T()` достаточно.
- **pino** (сервер). Полезен на большом сервере с системой сбора логов. Сейчас логи читает человек глазами, и `console` + `guard()` нагляднее. Вернуться при выходе в публичный онлайн.
- **Sentry и аналоги.** Своя отправка ошибок есть; внешний сервис — это лишние данные у третьей стороны и настройка.
- **express-rate-limit.** Лимиты в `accounts.ts` уже есть.
- **helmet.** Не нужен локально и в ПК-клиенте. Добавить при запуске публичного сервера в интернете (https://helmetjs.github.io).
- **@floating-ui/dom.** Подсказки у курсора уже работают с отражением у края экрана.
- **Vitest, Jest, Playwright.** Тяжелее того, что есть. Своя связка `tsx` + harness + `puppeteer-core` работает, а для новых модульных тестов есть встроенный `node:test`.
- **sharp, jimp.** Генераторы уже на `pngjs`. `sharp` — нативный и тяжёлый.
- **free-tex-packer-core.** Упаковщик со своими зависимостями для картинок. `maxrects-packer` + уже стоящий `pngjs` проще и легче.
- **Tiled, LDtk.** Карта процедурная и задаётся `data/world.json`, ручной редактор тайлов ей не подходит. Свой редактор конфигов (`editor/`) уже есть.
- **electron-store.** Свой `desktop/src/config.ts` уже работает.

## 6. Порядок внедрения (этапами, чтобы не ломать игру)

Правила для всех этапов:
- одна библиотека — одна задача и один коммит;
- после каждой задачи `npm run typecheck` и тесты из раздела этой библиотеки;
- сценарии с сервером запускать строго по одному;
- пакеты ставить с точной версией (`npm i -E`), чтобы обновления приходили только осознанно.

**Этап A. Без риска, только инструменты (1 короткая сессия).**
1. `npx knip`: отчёт, удаление явно мёртвых файлов небольшими порциями (3.6).
2. Biome только как линтер, без форматирования; отчёт → исправить `noFloatingPromises` (3.7).
3. `Intl.PluralRules` + разбор склонений в `T()` (3.4).

**Этап B. Надёжность сервера.**
1. Миграции через `user_version` (3.5) + тест на копии старой базы.
2. `zod`: обёртка в `makeOn`, затем группы сообщений по одной задаче (3.2). Тесты: `server-safety`, `trade`, `bank`, `combat`, `admin`.
3. `@colyseus/loadtest@0.16.2`: первый замер на 10–20 ботах, цифры записать в `docs/` (3.8).

**Этап C. Производительность на слабом ПК.**
1. Атлас объектов (3.1) — замер `perf-run` до и после.
2. Если выигрыш есть — атласы мелких листов юнитов и NPC.
3. `oxipng` в релизную сборку (3.10).

**Этап D. ПК-клиент.**
1. `electron-updater` + `electron-log` (3.3, 3.9). Обязательно проверить обновление 0.1.0 → 0.1.1 на чистой машине и сохранность базы.

**Этап E. По желанию.**
- `lit-html` для новых окон и горячих мест.
- `ZzFX` для звуков.
- `@colyseus/monitor` за паролем.

**Этап F. Крупные переезды — отдельные решения владельца, не раньше релиза.**

- **Colyseus 0.16 → 0.18.**
  - Документация: https://colyseus.io/blog/colyseus-017-is-here/, https://docs.colyseus.io/migrating/0.17, https://docs.colyseus.io/migrating/0.18
  - **Что даёт:**
    - встроенное предсказание движения и откат для попаданий (`Predict`, `allowRewindState`, `room.input()`);
    - `validate()` на zod — пригодятся схемы из этапа B;
    - `room.request()` с ответом;
    - автопереподключение клиента;
    - Express 5.
  - **Что ломается:**
    - `onLeave(client, code)` вместо `consented` — наша логика переподключения;
    - `colyseus.js` → `@colyseus/sdk`;
    - `@colyseus/schema` 3 → 5 с лимитом 63 поля на Schema — нужно проверить `Unit` и `SelfState` в `server/src/rooms/schema.ts`;
    - `onMessage` больше не заменяет обработчик при повторной регистрации;
    - свои коды закрытия 4xxx могут конфликтовать (`KICK_CODE`).
  - Ветка 0.16 ещё получает исправления: 0.16.26 вышла 06.09.2026, так что срочности нет.
  - Объём **L**, лучше двумя шагами: 0.17, затем 0.18.
- **Phaser 3.90 → Phaser 4.**
  - Phaser 3.90 (май 2025) — последняя версия третьей ветки. Phaser 4.0 вышел 10.04.2026, сейчас 4.2.1 (https://phaser.io/download/phaser4).
  - Официальное руководство по переходу: https://github.com/phaserjs/phaser/blob/master/changelog/v4/4.0/MIGRATION-GUIDE.md
  - Новый рендер может дать прирост на слабых GPU.
  - **Затронет:**
    - наши самописные шейдерные приёмы и тени (`shadows.ts` с раскладкой матрицы скоса);
    - `RenderTexture` для теней стен;
    - частицы;
    - `GearLayers.ts` и `UnitView.ts`.
  - Делать после атласов (этап C): атласы останутся полезными и в Phaser 4.
  - Перед решением — пробная ветка на 1 сцену и замер `perf-run`.
  - Объём **L**.
